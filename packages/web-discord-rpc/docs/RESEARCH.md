## Consequences recorded in the design

- Desktop IPC is primary, arRPC is the fallback; forced preferences never cross. The statuses and the `mixed` transport follow from that order. IPC-first means the pipe scan, not necessarily the desktop app: a pipe owned by arRPC still satisfies the IPC leg.
- One application ID serves both cards because `name` (`YouTube` / `YouTube Music`) overrides the card title; the ID itself is public and grants nothing. (Crunchy sends no `name`, so its card title is the application name.)
- The `client_id` query on every arRPC probe is not optional: it is what lets arRPC and Vencord attribute the activity.
- `og:image` is preferred over MediaSession art on YouTube because the live probe showed it is higher resolution.
- The extractor never throws and the worker never trusts a non-`https` URL, so a hostile page cannot inject a button target.
