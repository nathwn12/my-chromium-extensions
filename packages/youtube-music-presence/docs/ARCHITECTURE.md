# Architecture

Music-only presence from the page to Discord desktop. The extension never publishes YouTube video activity and does not offer transport or per-site configuration.

## Data flow

```text
music.youtube.com
  extract-youtube.js -> content.js -> background.js
  background.js -> Chrome native messaging -> native host -> Discord desktop IPC
```

`extract-youtube.js` reads media-session/player metadata and the actual `<audio>` or `<video>` element. `content.js` reports changes from media events, SPA navigation, visibility and page lifecycle; a one-second poll catches title and pause changes, and also re-reports when the live position drifts more than 2.5 seconds from where the last sample says it should be at the reported playback rate — and only when the position actually moved — so a seek the player never announced still re-aligns the card while buffering and non-1× playback stay quiet. `background.js` retains tab state in `storage.session`, selects the best playing tab, coalesces sends, and reconnects/replays after worker or Discord restarts. The accessible popup switch persists in `storage.local` and clears presence when switched off.

## Wire and activity

The worker opens one native port with `transport: "ipc"` and the built-in application id `1566530911514923188`. Only `source: "youtube-music"` reports are accepted. The host carries the activity to a Discord desktop named pipe; a report for any other source is rejected by the extension path.

The outgoing `SET_ACTIVITY` activity is type `2` (LISTENING), with `name: "YouTube Music"`, title in `details`, artist in `state`, and `status_display_type: 1` to request that Discord use the state in its member list. The expanded header remains `Listening to YouTube Music`. The artist line comes from the player bar's artist anchors, then MediaSession, then a structured JSON-LD author, and is absent when none resolves: an arbitrary byline segment is never read as an artist, so a localized view count cannot be mistaken for one. The card carries no link fields — no `details_url`, `state_url` or `large_url` — because Discord underlines every linked line and there is no link without the underline, so the title, artist and album are plain text and the two buttons are the only click targets. Tests inspect the outgoing IPC payload; actual Discord rendering has not been observed in this seam.

| Field | Rule |
| --- | --- |
| `details`, `state` | Collapsed, trimmed text, capped at 128 characters. Artist is preferred for state; then a distinct album; then the source label. |
| `assets.large_image` | HTTPS artwork only. The cover is not a link. |
| `assets.large_text` | The cover tooltip: the album when it is distinct from the visible lines, otherwise the YouTube Music view count when the player bar reports one, otherwise omitted. A value that only repeats a visible line is dropped, it never repeats the track title, and a view count is never treated as an album name. |
| `buttons` | At most two, HTTPS and on `music.youtube.com`, URLs capped at 512 characters and labels at 32. Each target is shape-checked: a track URL must be a `/watch` page with an 11-character video id, an album URL a `/browse/MPRE` page, an artist URL a `/channel` page; anything else is dropped rather than repointed. The first targets the track URL, with the current page URL as the last resort; the second is "View album" when an album link exists, otherwise "View artist", and is absent when neither exists. That second label is decided from URLs, never from text. |
| `timestamps` | Only when playing and both a real finite position and positive duration exist. Integer seconds on the wire: `start = floor(anchor/1000) - floor(clampedPosition)`; `end = start + floor(duration)` at every rate, so the total is the real duration and a 3:27 track never stretches or shrinks with playback speed. `now` enters as milliseconds. `now` is the instant the position was **sampled**, never the instant the payload is sent: the anchor is a function of the sample alone, so rebuilding one sample yields a byte-identical activity and no watchdog tick, coalesced send or replay can move the bar. `sampleAt` prefers the content script's own stamp, falls back to worker receipt time, and ignores a stamp more than five seconds ahead of that receipt time as junk — the reference is always a stored instant, never a clock read at build time. Missing elapsed or duration means no timestamps; elapsed and duration are never invented. |

The native host uses nonce-matched Discord IPC frames and retries after disconnect. The extension sends the current desired state on reconnect; the host replays its last activity across a pipe reconnect. The anchor is a function of the sample, never of the send, so that replay re-emits the same `start` instead of restarting the progress bar at replay time.

## Extraction and limits

Metadata precedence is MediaSession, Music player bar, JSON-LD, Open Graph title, then document title. Playback values come from the real media element only; JSON-LD duration may help identify a track, but does not create an elapsed position or make a paused/missing media element into playing playback. Timing is accepted only when it belongs to the displayed title: a player-bar `M:SS / M:SS` clock and a media element must agree, and a lone source is used only when there is no second one to disagree. During a handoff, disagreement in either direction withholds timestamps until the sources agree or the duration moves; two displayed clocks that disagree are the same withholding, never a missing clock that falls back to the element. A stale pair that agrees is held by the content script unless a changed total carries an owned reset: a playhead at or near zero, a coherent source new to the last published timed sample, or on a new identity a coherent total that differs from both the held and the credited total and whose playhead agrees with the shown clock. That reused-source mid-song path requires a trustworthy player-bar clock: one displayed clock, no conflict, and agreement with the chosen element on both total and playhead. With no bar clock, or with a clock that disagrees, the changed-identity mid-song path is not taken; those reads are deliberately held, not a universal first-read guarantee, and live-page behaviour there remains unverified. A new track sharing the outgoing total is likewise held. An owned first read publishes at once, so a genuinely fresh new duration is not held forever when ownership evidence exists. `sourceEvidence()` is non-null only when the extractor picked an element that matches the clock's total; `clockAgreesOf()` adds local-only proof that its playhead matches the clock too, so an outgoing element that matches only the total cannot unlock a hold. A bare `currentSrc` string proves neither. A new source at the old total stays blocked, because an outgoing element or an ad can change the source while the duration still belongs to the previous song. On a hold for the same track the baseline is the last published timed source, never a withheld read's source, so a changed total under that source stays outgoing. Wall time alone never releases a hold, and a withheld read never becomes the baseline for the next decision. Track identity includes the artist line, so a header-only change also arms the hold. A one-shot guard survives a blank navigation so a stale clock cannot cross it, then binds to the first read on the new page. The selected source stays local to the extractor and never enters the activity sent over RPC. An absent duration during a handoff holds the last credible duration instead of clearing the gate, so a stale duration returning under the new identity is still withheld; absence never counts as fresh. Arming and suppression both compare durations in floored integer seconds, the unit the activity builder stamps; a fractional media duration of 366.4 and an integer bar clock of 366 are therefore the same held second, with no bit-exact bypass. No large backwards playhead reset is treated as a fresh source on its own, since an outgoing seek or loop can produce the same shape. A player-announced `seeking`/`seeked` that moves the playhead backward reopens a hold only when the media is playing and the read matches the last published timed sample's identity, duration unit, non-null coherent source and playhead; a paused seek, a clock conflict, a changed total and a stale handoff stay withheld. The baseline is local to the content script and never enters the RPC state. An unassociated `loadedmetadata` from the outgoing element never approves a stale pair. A trusted media element supplies the pause state; MediaSession playback fills in only when no element is trusted. Multiple playing media must agree on elapsed time as well as duration, or timing is withheld; agreeing elements are one track, never a DOM-order pick. A duration appearing with an owned reset is a poll-triggered refresh; a position appearing at an unchanged duration is not. With no coherent evidence the extractor emits playing metadata without timestamps rather than borrow a previous, hidden or paused element's position and duration. Text and URLs are bounded before they cross the boundary. The content script runs only in the top frame, ignores `timeupdate`, and clears the tab on pagehide or navigation off Music.

The worker publishes the selected tab's latest state: ordinary updates are paced at one per 1.5 s with a ceiling of eight per rolling 20 s, so a seek or a pause lands within 1.5 s while the eight-per-20 s ceiling has room. A change of identity — a new track, artist line or album — is published immediately, even inside that 1.5 s floor, so switching songs is instant; the floor and that immediate change both hold only while the eight-per-20 s ceiling has room, and past it the next update waits for the window to expire. A queued update is dropped when the desired card returns to the published one or when the port dies, so a payload queued for a state that is no longer true is never sent later. Two edges remain: a rate change the player never reports can mask or delay one drift report until the next poll, and buffering can still produce a single report. The native host keeps its own budget and that budget is deliberately looser than the worker's: it never adds latency to a send the worker already allowed, it only guards the pipe against a runaway client. The worker persists tab state through service-worker suspension. Presence off sends an explicit clear and closes the port. Page/player DOM redesigns can still require selector updates; the extension does not inspect or capture media streams.

## Rate tracking

Discord's activity timer counts `floor(now − start)` in wall time, and no RPC field carries a playback rate. Between updates Discord interpolates that timer in wall time, so a track played faster or slower than 1× cannot literally run at its rate; the card cannot show 1.5×. The end is not rate-scaled: `end = start + floor(duration)` always, so the total stays the real 3:27 and never becomes 4:51 at 0.70× or 2:42 at 1.30×. While the rate is not 1× the worker re-anchors the elapsed reference on a 2.5 s floor (`RATE_INTERVAL_MS`) under the unchanged eight-per-20 s ceiling; identical payloads are deduplicated, so the measured re-anchor cadence is about 3.3 s, not 2.5 s. The elapsed reference is biased by half the interval's drift, `(rate − 1) × 1.25 s` — ±375 ms at 0.70× and 1.30× — bounded by the position already played so a track at 0:00 reads 0:00; the bar crosses the truth instead of always lagging. Integer-second stamps still let the elapsed bar read up to 1123 ms off the media position at 1.30× (3 of 5 samples) and 377 ms at 0.70× — that is the honest bound left by one-second stamps and the ~3.3 s re-anchor gap, and the send budget is not loosened to chase it. A burst beyond eight identity changes in 20 s defers to the window edge rather than raising the ceiling. At 1× no re-anchor runs and pacing is unchanged.
